Architecture

System Overview

The system takes raw documents from a local folder, transforms them into structured vector embeddings, stores them in Qdrant Cloud with rich metadata, and exposes a query interface that retrieves the top-N most semantically relevant chunks for any natural-language question.

Pipeline

Step-by-Step: How It Works

1

File Discovery & Loading

The ingestion script scans data/raw/ recursively and dispatches each file to the appropriate loader based on its extension. Each loader returns a list of RawPage objects — one per PDF page, Excel sheet, etc. — each carrying the extracted text and source metadata (filename, file type, page number).

.pdfpymupdf (fitz)Page-level extraction; preserves page number
.docxpython-docxParagraphs + tables tagged [TABLE]…[/TABLE]
.xlsx / .xlspandas + openpyxlPer-sheet pages; header row preserved
.csvpandasColumn headers included as first row
.htmlbeautifulsoup4Scripts/styles removed before extraction
.txt / .mdstdlibUTF-8 direct read
.jsonstdlibPretty-printed representation
2

Structured-Based Chunking

Raw pages are parsed into typed structural elements, grouped under headings, then split or merged to fit the target chunk size. See the Chunking section for full details.

Each chunk carries a rich metadata payload: section breadcrumb, page number, source file, character count, and chunk index. This metadata is stored alongside the vector in Qdrant and can be used to filter search results.

3

Embedding Generation (with Cache)

Each chunk's text is passed to the embedder. Before calling the model, the cache is checked: if a SHA-256 hash of the text already exists in the disk cache, the stored vector is returned immediately. Only cache misses invoke the model.

4

Upload to Qdrant

Chunks and their embeddings are batched and uploaded to the Qdrant collection as PointStruct objects. Each point has:

  • A UUID as the point ID
  • Named vector(s): "dense" (and "sparse" in hybrid mode)
  • Full metadata payload (text, source, section, page, timestamps, etc.)

Already-ingested files are skipped on subsequent runs (tracked by source_file in the payload). Use --force to re-ingest or --recreate to start fresh.

5

Query & Retrieval

A natural-language query is embedded using the same model used at ingestion time. Qdrant performs an approximate nearest-neighbour search and returns the top-K most similar chunks with their cosine similarity scores (0–1).

In hybrid mode, Qdrant runs two searches in parallel (dense and sparse), then fuses the ranked lists using Reciprocal Rank Fusion (RRF) — a parameter-free method that gives good results without manual tuning.

Core Component

Structured-Based Chunking

This is the most impactful design choice in the system. Instead of splitting text every N characters (naive), the chunker respects the document's own structure.

🚫

What NOT to do (naive)

Fixed-size splitting every 512 characters. Fast to implement, but:

  • Cuts mid-sentence
  • Separates table header from rows
  • Merges unrelated sections
  • Poor retrieval quality
✅

Structured approach (used here)

3-phase algorithm that follows the document hierarchy:

  • Parse into typed elements
  • Group under parent headings
  • Split oversized sections at sentence boundaries
  • Add overlap between chunks

The 3 Phases

Phase 1 — Parse
Detect structural elements: heading (H1–H6), paragraph, table ([TABLE]…[/TABLE]), code (fenced blocks), list (bullet/numbered). Code and table blocks are never split.
Phase 2 — Group under headings
Maintain a section breadcrumb ("Intro > Concepts > Definitions"). Accumulate elements until the group would exceed CHUNK_SIZE. When the limit is reached, flush the group as a chunk and start fresh under the same heading.
Phase 3 — Overlap context
Prepend the last CHUNK_OVERLAP characters of the previous chunk to the next chunk. This ensures answers that straddle a chunk boundary are still retrievable.

Embeddings

Embedding Strategies

⚡

DenseEmbedder (default)

Uses sentence-transformers/all-MiniLM-L6-v2. Produces 384-dimensional L2-normalised vectors. Distance metric: Cosine.

Chosen for its speed + quality balance for English. Trained on MS-MARCO, NLI, and other English sentence pairs. ~14k sentences/sec on CPU.

🔀

HybridEmbedder (ready)

Dense vector + sparse BM25-lite vector. The sparse part uses the hash trick to map tokens to integer indices without needing a fixed vocabulary or corpus statistics.

Enables both semantic and keyword matching. Qdrant fuses results with RRF.

💾

Embedding Cache

Every computed vector is stored in diskcache keyed by sha256(text) + model_name. TTL: 24h. Size limit: 2 GB.

On re-ingestion runs with unchanged documents, ~97% of embeddings are served from cache, reducing runtime from minutes to seconds.

Why cosine similarity?

Cosine similarity measures the angle between two vectors, ignoring their magnitude. This is ideal for semantic search because it captures direction of meaning, not just how long the text is. Since we L2-normalise vectors before upload, cosine = dot-product in Qdrant, which is faster to compute.

Why the hash trick for sparse vectors?

Problem with standard BM25: IDF (Inverse Document Frequency) requires knowing how many documents contain each term — a corpus-wide statistic. For incremental ingestion, this means you'd need to re-compute all vectors every time new files are added.

The hash-trick approach computes a per-document TF vector with log-normalisation, mapping each token to a fixed integer bucket via hash(token) % VOCAB_SIZE. This is statistically similar to BM25's keyword recall properties without any corpus dependency.

Why store the full text in the payload?

Qdrant is the single source of truth. Storing the chunk text in the payload means the application doesn't need a separate document store — one query to Qdrant returns both the ranked chunk text and all metadata needed to cite the source.

Scripts Reference

ingest.py

# Ingest all files (dense, default)
python scripts/ingest.py

# Hybrid mode
python scripts/ingest.py --mode hybrid

# Single file
python scripts/ingest.py --file report.pdf

# Dry run (no upload)
python scripts/ingest.py --dry-run

# Force re-ingest
python scripts/ingest.py --force

# Custom chunk size
python scripts/ingest.py --chunk-size 768 --overlap 96
🔍

query.py

# Basic query
python scripts/query.py "What is RAG?"

# Hybrid mode
python scripts/query.py "RAG" --mode hybrid

# Top 10, full text
python scripts/query.py "RAG" --top-k 10 --verbose

# Filter by source file
python scripts/query.py "KPIs" \
  --filter source_file=report.pdf

# Minimum score + export
python scripts/query.py "metrics" \
  --min-score 0.5 --output results.json

Design Rationale

Key Technical Decisions

Qdrant Cloud (free tier)
Managed, serverless, no infra to maintain. Free tier gives 1 collection with up to 1M vectors at 384 dimensions — more than enough for a POC corpus. Named vectors let us support both dense and sparse vectors in the same cluster without extra cost.
sentence-transformers over OpenAI embeddings
No per-token API cost, no internet dependency at inference time, runs locally. The all-MiniLM-L6-v2 model is freely downloadable and well-benchmarked. Swapping to OpenAI's text-embedding-3-small would only require changing the DENSE_MODEL env var and adding the openai package.
Structured chunking over sliding window
Document structure carries semantic meaning. A heading like "Limitations" signals that the following paragraph is about constraints — keeping them together produces a more coherent chunk. Retrieval precision improves significantly on structured documents.
Hash-trick sparse vectors over corpus BM25
True BM25 IDF requires corpus-level statistics that change with every new document. The hash trick gives incremental ingestion without sacrificing keyword recall. For production, replace with a proper sparse model (SPLADE / FastEmbed's BM25).
diskcache over Redis / in-memory for embeddings
For a POC, a file-based cache is zero-infra (no Redis server needed), persistent across restarts, and fast enough for batch ingestion. Upgrade path: swap to Redis for multi-process or distributed setups.
Payload = single source of truth
Storing the full chunk text inside the Qdrant payload means one round-trip returns both the relevant text and all metadata. No secondary lookup into a document store needed. Trade-off: slightly larger payloads, but negligible at POC scale.
